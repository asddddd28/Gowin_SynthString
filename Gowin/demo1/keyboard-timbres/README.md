# 五类基础音色：以声音需求驱动硬件扩展

第一步沿用已验收的 `keyboard-latency` 固件，新增 16 个基础音色、32 键示范库和 App 分类/试听功能。本轮没有增加 RTL、改变采样率或重新烧录；先确认现有模块的可用范围，再扩展缺少的声音能力。

## 当前可以尝试的声音

| 类别 | 第一批音色 | 已有硬件的用途 | 明确缺口 |
|---|---|---|---|
| Drum | 低频鼓击、FM 通鼓、木质敲击、金属短击，共 4 个 | 正弦/FM/Ring、短振幅包络、短调制包络、LP/BP | 低频鼓击没有音高下滑；金属短击不是噪声踩镲。军鼓/踩镲需要噪声源 |
| Bass | Sub、锯齿低音、FM 弹拨低音，共 3 个 | 低八度、双振荡器、固定低通、调制深度衰减 | 动态 Filter EG、音高包络、滑音和单音连奏 |
| Pad | 温暖铺底、双锯齿弦垫、柔和泛音垫，共 3 个 | 慢起音、微失谐、长释音 | LFO、持续音实时滤波调制、立体声/Chorus/Reverb |
| Key | FM 电钢、晶莹钟键、短音拨键，共 3 个 | 两算子 FM、独立调制包络、振幅衰减 | 不是采样钢琴或完整物理建模；更细的速度响应和包络曲线待扩展 |
| Chord | 短促和弦、电钢和弦、柔和和弦垫，共 3 个 | 多个琴键/声部共同演奏，沿用复音响度补偿 | 本阶段不做单键自动和弦；后续扩展声像、立体声与效果 |

这些名称表达声音设计目标，属于基础合成近似，不代表 Surge 原厂音色兼容或真实乐器复现。音色描述仍需要人工听音评价。

## 使用

1. 运行 `app/TangSynthStudio.exe`，连接 COM4；支持现有 Studio 协议 3/4。
2. 点击“载入五类示范分区”。App 保留载入前的 32 键库，并暂停自动同步，避免只更新一个键造成混淆。
3. 点击“同步全键”，等待 32 个键位确认后演奏实体键。
4. 可按分类选择单个音色，用“试听当前键”播放；按“停止试听”或 Esc 停止。试听会自动松键，不受延音锁住。Pad 请给慢起音足够时间。
5. “恢复载入前的音色库”先恢复电脑参数，再点击“同步全键”恢复板卡。`baseline/User-bank-before.json` 另存了本次测试前从旧 App 导出的库。

直接导入文件为 `banks/FiveFamilies-bank.json`，沿用 `tang-axis-studio` 格式。原有 12 个起始音色仍保留，App 共显示 28 个入口。

| 实体键 | 分区 | 音高/操作 |
|---|---|---|
| K01–K08 | Drum | 四种打击音及不同音区变体 |
| K09–K14 | Bass | MIDI 36/38/40/41/43/45 |
| K15–K20 | Pad | MIDI 48/52/55/60/64/67，可组合铺底 |
| K21–K26 | Key | MIDI 60/62/64/65/67/69 |
| K27–K29 | Chord | 同时按下：C4/E4/G4，C 大三和弦短击 |
| K30–K32 | Chord | 同时按下：C4/E♭4/G4，C 小三和弦铺底 |

Chord 采用用户确认的“多个琴键共同演奏”方案。一个键仍是一个声部；Pad、Key、Bass 也可多键组成和弦。

## 下一轮硬件增量

以当前五类声音为需求，建议按下面的顺序实现和验收，不直接一次加入整个 Surge。

1. **Pitch EG + 噪声源**：音高包络用于底鼓下滑、通鼓和弹拨低音；每声部独立噪声状态用于军鼓、踩镲和敲击瞬态。现有第二包络和相位计算可参与复用，但新增调制目标、噪声状态和协议能力仍需实际设计/仿真/PnR。
2. **Filter EG + 参数平滑**：让 Bass、Pad、Key 的明暗随音符变化；滤波系数更新必须限幅、平滑并检查递归稳定性。先做少量明确的调制目标，再扩成矩阵。
3. **LFO + 立体声**：独立控制颤音/颤幅/截止频率，增加声像和铺底宽度。随后按存储与周期预算接入 Chorus、Delay、Reverb。
4. **复杂键盘音色与素材**：需要真实钢琴等音色时，再接回 PCM 播放、SD/exFAT 资源加载及多素材缓存。

新增能力应有显式的协议能力标志，旧固件不能把无法支持的音色标记为同步成功。继续采用共享计算核心、逐声部状态和参数快照；不因新增一个逻辑振荡器或包络就复制整条物理流水。

当前监测版为 32 逻辑声部、每声部双振荡器/双 ADSR/单 SVF，385/1024 拍。实现占用 CLS 85%、BSRAM 80%、DSP 63%，50 MHz 时序余量很小；扩展前优先压缩监测/状态存储，再做实际资源与时序评估，不能只按剩余采样周期推算装得下。

## 验证与证据

- `prepare_library.py`：生成示范库和独立 Python 编码参考。正数半值向上量化与 Rust App 约定一致；旧 Python 模型的偶数舍入曾在 1 LSB 边界被交叉测试检出，未改动固件或生产编码器。
- Rust `foundation_library_matches_independent_profile_model`：16 个音色及 32 个示范键位的 64 字节配置逐字节一致，检查 C 大/小三和弦音高。日志在 `reports/profile_tests.log`。
- TypeScript/Vite 和 Rust release 构建：`reports/app_build.log`、`reports/release_build.log`。
- `live_foundations.py`：逐音色下发配置、检查 ACK/非零音频/起音记录/释音结束，并测试两组三和弦；结束后恢复旧 App 导出的受影响键参数和原音量。此恢复依据 App 导出库，不声称做了 FPGA 参数回读。
- 实际板上结果以 `reports/live_foundations.json` 为准；原始串口字节在 `reports/live_serial.bin`。首轮曾出现两个不完整回传包，失败记录保留于 `reports/first_run/`，不得把该轮标成全通过。

本轮只对已有 RTL 做功能边界核对，未生成新的 RTL。编译、AST、可读性、注释、命名、profile、testbench、toolchain 等硬件门禁状态沿用上一阶段证据；严格风格门禁仍有未通过项，不将新的音色参数测试等同于新的 RTL 合格证明。
