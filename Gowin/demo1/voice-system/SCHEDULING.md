## 约束：吞吐与事件响应分开验收

- 音频输出周期1024拍，即20.48µs；稳态每周期交付一个双声道采样。允许固定、多采样周期的流水延迟。
- 输入事件到输出响应：上限1ms（50000拍），目标200–500µs（10000–25000拍）。起点为采集、去抖之后的按键事件或完整Note-On进入FPGA控制通路；终点为DAC输出首个受影响采样。
- 验证使用即时起音、含干声的确定性音色。音色主动设置的Attack、纯湿声Delay等音乐时间不等于调度开销。
- 数字仿真分别记录事件进入、命令生效、Voice完成、FX完成、PCM取出、PT8211帧发送完成。实际模拟DAC输出还需上板测量，不用PCM VALID冒充模拟发声时间。
- 深FIFO只能吸收抖动，不能补偿长期生产速率低于消费速率。必须同时统计延迟、启动间隔II、队列最高占用、overrun/underrun与丢包。

Voice一次只允许一帧在途，渲染周期也限制下一帧启动。FX已有独立输入队列，可与下一帧Voice重叠。原基线Voice874/整链948拍，预取候选786/860拍；整链延迟不能普遍当成各阶段的启动间隔。将来若40MHz且采样率不变，每采样约819.2核心拍，须重新验证时序和吞吐，不能只比较860与819.2。当前不改频率。

## 推荐结构

采用“驻留音色程序 + 有限在途窗口 + 依赖记录 + 每类执行器就绪队列”。音色在上位机编译为算子节点和依赖，驻留程序RAM；按键事件创建声部实例，音频帧生成该实例的采样任务，不从电脑逐采样发送整套指令。

控制器分成四个职责，物理上可以由小型RTL状态机与RAM表实现，不要求通用CPU：

1. **事件与版本管理**：按时间顺序应用Note-On/Off、CC与音色提交，分配声部generation；去重依据已有epoch/sequence/NoteID，持续按下不重复触发。
2. **依赖准备**：根据程序节点、源结果有效位与上下文状态完成位，找出可发任务。跨采样反馈显式引用上一帧状态；同一采样内的零延迟环路应在编译时拒绝。
3. **资源发放**：在执行器可接收、参数/源操作数可读、结果槽及完成队列信用充足时才发放任务。
4. **完成提交**：按tag定位目标槽，写回结果和状态，清除资源锁，唤醒依赖者；按帧号组织混音与输出，不按计算完成的先后顺序直接送DAC。

第一版保留当前算子与AXI命令ABI，先做“当前任务 + 下一个预取任务”两个工作槽。当前算子执行时读取下一算子的core/envelope/context；锁存当前任务仍需要的carrier、状态地址等元数据，避免RAM读地址提前切换导致完成结果写错位置。预取只能处理已满足依赖的部分，不能用尚未完成的FM源结果。

另一个优先项是将下一声部的路由调制与当前声部的算子执行重叠。必须分别保存当前声部的调制快照与下一声部的准备结果，禁止后者覆盖当前算子的gain/depth。满载8声部中，有机会隐藏后7个声部的14拍等待，即约98拍；这是待验证的上限估计，需扣除快照、存储端口和调度开销，不能预先承诺最终数值。

初期按一个Voice采样帧调度并允许FX跨帧重叠；验证完上下文与版本机制后，再扩大为两个采样帧在途。不要直接创建几十帧待执行任务来填满FIFO，这只会放大按键响应延迟。

## 环形pending队列如何使用

环形存储适合有限容量、高效入队出队，但不应让一个依赖未满足的任务挡住所有后续可运行任务。

| 队列/记录 | 用途 | 初始建议 |
|---|---|---|
| 事件环形队列 | 已采集的Note/CC/提交请求 | 小型有界队列；为Note-Off/Panic保留通路 |
| 等待记录表 | 保存未满足的源依赖、context锁与任务状态 | 由在途窗口推导大小，最初仅当前/预取槽 |
| 每类执行器ready队列 | 只存依赖已满足的任务ID | 每类2–4项作为起点，按实测占用调整 |
| 完成环形队列 | 接收异步或不同延迟单元的完成通知 | 发放前预留完成空间，避免完成端死锁 |
| PCM FIFO/帧提交表 | 按帧号交付固定速率输出 | 初期保留现有深度并测量；不盲目加深 |

各队列用读写指针及回绕位/计数区分满空，必须验证同时push/pop、回绕、满队列和取消。当前全部50MHz时是同步队列；将来跨时钟才使用经过验证的异步FIFO与复位同步，不把跨时钟多位数据直接接线。

“pending”必须区分**等依赖**与**已发出等完成**。后者仅凭tag等待结果，不能再次发放；源端VALID保持与AXI重试也不能生成第二次算子计算。

## 冲突处理规则

| 冲突 | 处理 |
|---|---|
| FM结果尚未产生 | 源ready位为0，任务留在等待表；其它声部可继续运行 |
| 执行器忙 | 按实际ready/II发放；单在途FM不能按LFO的II=1对待 |
| 参数/状态RAM读写端口冲突 | 调度时预留端口；使用固定优先级加轮转或预编译槽位；不能只看DSP是否空闲 |
| 同一voice/operator状态被两帧更新 | 每个context有busy/完成序号；下一帧等上一帧状态提交，禁止两个任务同时读旧状态 |
| 不同声部共享物理算子 | 各自context地址与generation独立；物理单元不持有隐式声部归属 |
| scratch结果槽被复用 | 分配时占用，消费后释放；tag带帧号/generation，拒绝迟到结果写入新任务 |
| 音色热更新 | 参数按版本/银行固定到明确的帧边界；旧版本在引用清零前不能覆盖，双缓冲不够时延迟提交 |
| 完成乱序 | 根据task ID写回并释放依赖；音频最终仍按frame ID提交 |
| 声部抢占、Note-Off或Panic | generation/epoch使旧任务失效；已执行任务返回时丢弃旧结果并释放预留资源，不直接写入新声部 |
| 队列满 | 停止接收或返回明确忙状态，记录高水位；不静默丢音符释放事件 |
| 死锁 | 发放前预留结果槽和完成信用；不要拿着context锁等待不能获得的完成槽 |
| 超期 | 记录deadline miss并采用明确降级策略；验收时要求正常负载下零超期，不能靠长期重复旧样本掩盖吞吐不足 |

对回授算法，状态更新与音频结果是两种依赖：下一采样的振荡相位/反馈可以在其context提交后准备，但不能据此越过本帧未完成的混音、滤波或FX状态依赖。

## 指令包与AXI预算

任务描述符建议携带task ID、frame ID、voice generation、opcode、context索引、program/param版本及源/目标slot引用。具体位宽按容量确定；参数、包络和波表驻留本地RAM/cache，避免每次任务传完整参数和状态。模块公开接口可以继续通过AXI-MM适配CMD/Completion FIFO。

当前FM输入包672bit=84字节，返回160bit=20字节。8声部×6算子×48828.125Hz，约234.375万次任务/秒。若将全部104字节按任务搬到32bit/50MHz AXI上，**仅FM就需要243.75MB/s**，超过200MB/s理想单数据通道峰值，还未包括协议等待、调制和FX。

这个数字是单共享数据通道/串行搬运的预算，不能据此断言所有AXI结构都只有200MB/s：AXI读写独立通道或多端口可以并行，但必须逐通道核算。即使输入与返回分别走两个独立方向，仅84字节请求已需196.875MB/s，几乎吃满一个32bit/50MHz方向的理想带宽，现实仍不合适。

若先按16字节描述符和8字节完成记录估算，FM控制流约56.25MB/s；数据读写及协议效率另算。这只是预算示例，不是已经定义的ABI。应使用驻留程序、缓存和burst批量灌入模块队列；现有UART→SynthAxiMaster邮箱事务用于低频配置，不适合变成每个音频算子的多寄存器往返控制流程。

AXI写响应只表示命令被接收，计算完成必须由带tag的Completion回报。控制器要分别追踪队列容量、AXI事务和计算任务，不能收到B响应就释放context锁。
