# 采集到 DAC 的实时延迟监督器

本工程在 `keyboard-parallel` 的 32 声部、385 拍合成引擎上增加只读监测。原并行工程未修改，原固件位于 `baseline/keyboard_parallel.fs`。新 App 位于 `app/TangSynthStudio.exe`；其源代码更新在 `demo_test/desktop-tauri` 的 Synth Studio 模块，修改前备份位于 `baseline/app/`。

## 测量边界

实体键从**第一个越过按下门限的 ADC 结果可用**开始计时，包含下一轮扫描确认的等待。远程或自测从 **FPGA 内部有效演奏状态的上升沿**开始计时，不包含电脑、USB 和 UART 的发送时间。

终点是 PT8211 **左声道 WS 下降沿锁存数据**：该帧必须包含这个声部的非零结果，而且混音、音量缩放、24→16 位舍入后的 DAC 字非零。若首帧为零，监督器继续等待；静音等情况下默认 1 秒超时，不把无声帧记成发声完成。

这是一项数字链路测量。机械按下到第一次被扫描、ADC 转换结果可用前的时间、DAC/功放模拟延迟和声学传播时间不在结果内。多声部混音时，非零数据也不保证目标声部已经达到可闻响度。App 将实体键和远程事件明确区分，并显示该键最近的完整扫描周期；机械按下还可能额外等待一个扫描周期。

## 分段时间

所有时间戳来自同一个 50 MHz 计数器，一拍 20 ns。总延迟精确等于以下五项之和：

| 项目 | 起点 → 终点 |
|---|---|
| 扫描确认 | 首个门限候选 → 第二次扫描确认；远程为零 |
| 事件排队 | 确认 → NoteOn 参数被合成引擎接受 |
| 首轮计算 | 参数接受 → 这个声部的第一个 SVF/VCA 返回 |
| 非零起音等待 | 第一次返回 → 最终用于起音的非零声部返回 |
| 混音及 DAC 等待 | 该非零返回 → 对应非零帧的左声道锁存 |

`mix` 单独给出非零声部返回到 PCM 提交的时间，它已经包含在最后一项中，不能再次加到总延迟。32 位时间戳约 85.9 秒回绕，通过模减处理；事务在 1 秒内完成或超时。默认告警预算为 10 ms，可通过顶层 `C_LATENCY_BUDGET` 在综合时调整。

每键一个事务，32 键独立记录。新起音覆盖尚未完成的旧事务时计入覆盖数；代号比较阻止旧结果误报为新事件。所有观察信号先寄存一拍，同时携带原始时刻，避免高扇出逻辑直接挂到音频引擎输出。完成后用共享快照/差值/发布流水汇总，32 键同时完成最多约 36 拍读出，读出排队时间不计入延迟。监督器不向音频路径施加背压，不改变音频内容、采样率或 385 拍引擎预算。

扫描周期只用一个减法器计算。PCM 和 DAC 完成时间戳按帧共享：同一个左字锁存沿完成的事务属于同一帧，36 拍内汇总完毕，早于下一次相隔 1024 拍的锁存沿。该监测器针对本工程固定音频帧率；若修改输出节拍，必须保证完成批次在下一帧前排空，或改成逐帧队列。

## App 和协议

App 顶部新增延迟面板：最近值、最小/平均/最大值、五段耗时、预算告警、超时、覆盖、取消候选、等待中键数，以及实体/远程事件数量。支持 `L` 命令清零监测统计；不会复位声音、音色或键盘。

统计覆盖 FPGA 完成的全部事件。UART 发送的是周期快照，密集连奏时最近事件明细可能跳过；曲线和导出的 CSV 是最近最多 80 个回传快照，不是无损逐事件日志。原始 App 遥测可以用 `--capture <路径>` 保存为 JSONL。

遥测版本为 **4**，长度 **192** 字节，头 `A5 5A 04 C0`。0～77 字节保留 Studio 公共字段，78～79 保留。190 是 0～189 的 XOR，191 是 CR。音色、波表、音符、音量等命令保持原 CRC16 协议。新版 App 同时接受版本 1、2、3、4；音色编辑和演奏支持 3/4，旧固件不伪造延迟读数。

延迟扩展的所有整数均为小端，时间单位为 50 MHz 时钟拍：

| 字节偏移 | 字段 |
|---:|---|
| 80 | 完成计数 u32 |
| 84 / 85 | 最近键号 u8 / 标志 u8：物理来源、声部非零、DAC 非零、超预算 |
| 88 / 92 / 96 / 100 | 总延迟 / 扫描确认 / 排队 / 首轮计算，各 u32 |
| 104 / 108 | 输出等待 / 其中的混音耗时，各 u32 |
| 112 / 116 / 120 | 最小 u32 / 最大 u32 / 累计总拍数 u64 |
| 128 / 132 / 136 | 超预算 / 超时 / 覆盖计数，各 u32 |
| 140 | 最近物理键完整扫描周期 u32 |
| 144 / 148 | 物理 / 远程完成计数，各 u32 |
| 152 / 156 / 160 | 当前时钟 / 最近起点 / 最近 DAC 锁存时间戳，各 u32 |
| 164 / 168 / 172 / 176 | 预算 / pending 位图 / 非零起音等待 / 候选取消数，各 u32 |
| 180～189 | 保留 |

## 已执行的验证

- `latency_model.py`：独立时间差合同、32 键及时间戳回绕。
- `run_test.py latency_supervisor`：34 个确定时序结果，验证各段精确数值、回绕、32 键并发、候选取消、零结果/零 PCM、静音超时、新事件覆盖、清零。
- `run_test.py latency_keyboard_audio`：15,586 帧音频、15,585 个串行帧、70,931 次 ADC 转换；32 个物理键及 5 个远程事件完成计时。监测起点与实际 ADC 候选一致，终点与串行 WS 下降沿一致，分段之和精确等于总时间，音频计算保持 385 拍。测试使用加速扫描参数，其延迟数值不作为板上扫描延迟。
- Rust 协议解析测试：版本 4 的全部 193 种分包边界、64 位和、坏包恢复，以及旧版本 3 的 ACK 兼容通过；TypeScript 和 App release 构建通过。
- 首轮集成发现复制工程时遗漏 `rtl/synth/sine.mem`；失败记录保留为 `reports/missing_rom_*`，已补齐并通过完整重测。烧录检查明确拒绝带缺失 ROM 警告的构建。

实际实现、烧录及上板结果以 `reports/gowin_summary.json`、`preflash.json`、`program.log`、`live_validation.json` 和后续用户听感记录为准。`program_verified.py --program` 先检查仿真源码指纹、原工程未改、ROM 一致性、50 MHz 时序，再独占串口并下载 SRAM；不写 Flash，也不声称完成整片 SRAM 回读。

这些实测表明当前实体键延迟主要来自两次扫描确认。机械按下到第一份 ADC 结果仍可能再等约一个扫描周期，因此实测约 6.7 ms 不是完整机械响应时间。下一步降低整体演奏延迟，应先验证多路复用稳定时间和判键去抖要求，再决定是否缩短扫描周期。

`reports/app_validation.json` 保存 App 回传的数值一致性检查、并发按键观测和听感确认状态。2026-11-02，用户通过底板 3.5 mm 耳机接口确认：“单键和和弦都正常发声”。本轮数字链路检查与人工听音均已通过；该听感确认不作为声学延迟测量。运行 `summarize_board.py` 会重新生成当前日志快照，需通过 `--hearing` 明确携带听感结论，并保留本次验收记录。
